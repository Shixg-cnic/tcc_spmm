1. 首版 kernel 固定成什么样
项目	首版设计
基础 CW	8 个源列，继续使用你的列式 bitmap 格式
SW 大小	固定 4 个 CW，即最多 32 个源列
一个 thread block一个 线程块	处理一个 SW 的 128 维特征
线程配置	128 线程，4 个 warp
每个 warp	处理 32 个特征维度
F=128	每个 SW 启动 1 个 block
F=256	每个 SW 启动 2 个 block，分别处理两段特征
X 的保存位置	优先放寄存器，加载后直接转成 TF32 fragment
输出部分和	放 shared memory，只保存仍有后续贡献的行
全局输出	一个 SW 内，同一目标行最终只提交一次
A 加载	先完成同步版本，再接双缓冲


这一版要解决两件事：让每次全局输出包含更多有效贡献，并让 X 的加载和转换结果被充分复用。
例如，某个输出行 17 同时出现在 CW0、CW1、CW3 中。原来三个 CW 分别向 Y[17, :] 做原子累加；新核先在 block 内把三份贡献合起来，最后向 Y[17, :] 提交一份。
对于 F128，这一行对应的全局标量更新就从 \(3\times128\) 次降为 \(128\) 次。
但实现之前必须先解决成员分组：如果放进同一个 SW 的 CW 几乎没有共同输出，缓存就很难产生收益。
2. 轻量重排：先改变源列分组，保持数学矩阵不变
这里重排的是“哪些源列放进同一个 CW/SW”。X、Y 对外仍使用原始节点编号。
为什么需要这一步
仓库保存的 Products 统计中，原编号 Q4 分组即使把 SW 内重复输出全部合并，可减少的逻辑更新比例也只有约 0.172%。因此，直接在现有相邻 CW 上增加 shared 缓存，收益空间很小。对应结构统计
重排需要同时改善两个层次：
- **CW 内：**让几个源列共享更多目标行，使一个 8×8 tile 包含更多非零元素，减少 tile 数和 CW 输出行数。
- **SW 内：**让不同 CW 共享更多目标行，使跨 CW 的部分和能够合并。
首版采用一个足够简单的算法
先采用 一个固定 MinHash 签名排序，再在 32 源列小组内贪心构造 CW。暂时不实现上一版复杂的多签名候选池。
具体步骤：
1. 从 CSR 构造结构 CSC。
   对每个源列 \(c\)，得到它对应的目标行集合 \(N(c)\)。这里只用于分组，A 的浮点权重继续保留。
2. 为每个非空源列计算一个固定签名。
   \[
   s(c)=\min_{r\in N(c)}h(r)
   \]
   \(r\) 是目标行号，\(h\) 是固定种子的 64 位 hash。按 (签名, 度数, 原始源列ID) 排序，零度源列放到最后。
   签名用于便宜地提出初始分组。不同签名的数值相邻，并不保证邻居相似，所以最终必须看结构和时间结果。
3. 每连续 32 个源列形成一个小组。
   这个小组最后产生最多 4 个 CW，直接对应一个 Q4 SW。
4. 在小组内构造 8 列 CW。
   从尚未使用的最高度源列开始，然后每次选择与当前 CW 目标行并集重叠最多的源列：
   \[
   \operatorname{gain}(c)=|N(c)\cap R_{\mathrm{CW}}|
   \]
   \(R_{\mathrm{CW}}\) 是当前 CW 已经覆盖的目标行集合。选满 8 个源列后，再构造下一个 CW。平局规则固定，保证重复执行得到相同结果。
5. 用一次 目标行 → 32位成员掩码 加速组内计算。
   掩码表示这个目标行与组内哪些源列相连。维护增量 gain，避免每次重新计算大量集合交集。
6. 给极大邻接设置预算。
   首版可将每组邻接条目预算固定为 262144。先检查组内度数总和，超过预算就按当前顺序每 8 列构造 CW，记录回退次数。
这条路线只有固定小组内的搜索，比较容易实现和测量。
数据格式必须增加显式源列映射
增加：
cwCols[8 * cw + k]  // CW 内第 k 个源列对应的原始节点 ID

以后加载 X 使用：
const uint32_t src = cwCols[8 * cw + k];
const float value = X[size_t(src) * F + feature];

不能继续用 cw*8+k 当原始源节点。
然后重新生成 CW 的目标行、bitmap 和 values：
- CW 内源节点按原 ID 排序；
- 目标行严格递增且唯一；
- 每最多 8 个目标行构成一个 tile；
- bitmap 的位置仍是 rowInTile*8+sourceInCW；
- values 按 bitmap 置位顺序保存；
- 重建出的坐标和权重必须与原 CSR 一致。
**先做恒等 cwCols 验证，再打开分组。**这样能够区分格式错误和分组算法错误。
3. SW kernel 的核心：交错处理 CW，按输出生命周期累加
这一部分是第一步真正需要实现的新 kernel。
用 tileMax 顺序交错处理 4 个 CW
不要先把 CW0 全部做完，再做 CW1。这样同一个输出行的两次贡献可能相隔很远，需要长时间保留大量部分和。
改成：
- 每个 CW 指向自己的第一个未执行 tile；
- tileMax 是这个 tile 中最大的有效目标行；
- 每次选择 tileMax 最小的 CW，执行它的当前 tile；
- 然后只推进这个 CW。
伪代码：
while 四个 CW 中还有未处理 tile:
    c = 当前 head tile 的 tileMax 最小的 CW
    输出这个 tile 到执行顺序
    推进 CW c 的 head

这份顺序在 CPU 上生成，GPU 直接读取。
**CW 内目标行有序，加上这种归并顺序，可以限制同时存活的输出行数量。**刚处理完一个 tile 后，未完成的输出行至多落在其他三个 CW 的 head tile 中，即最多 24 行；下一 tile 最多再引入 8 行，所以 Q4 使用 32 个输出槽作为安全容量。
这个结论依赖有序、唯一的目标行和上述执行顺序，不能随意换顺序后继续沿用。
每个输出行只需要两个状态位
离线扫描执行顺序，标记每条 tile 行：
- HAS_PREV：这个 SW 中，前面已经出现过该行；
- HAS_NEXT：这个 SW 中，后面还会出现该行。
GPU 的行为为：
状态	MMA 前的 C	MMA 后的处理
前面没有、后面没有	0	提交全局输出
前面没有、后面还有	0	保存到 shared
前面有、后面还有	从 shared 读取	更新 shared
前面有、后面没有	从 shared 读取	提交全局输出


关键实现是：
C = HAS_PREV ? shared 中的旧部分和 : 0
C = MMA(X_fragment, A_fragment, C)

if HAS_NEXT:
    shared 中的部分和 = C
else:
    atomicAdd 到 Y

**直接把旧部分和作为 MMA 的 C 输入。**这样最后一次出现时，可以直接提交 C，省掉“先写回 shared，再读出来 flush”的步骤。
shared 中每个有效输出元素只有一个线程负责，使用普通 load/store；tile 之间用 block 级同步保证可见性。
槽位由 CPU 提前分配。某行在一个 tile 中结束后，其槽位只能从下一个 tile开始复用，防止当前 tile 的不同线程互相覆盖。
首版元数据保持精简
继续使用基础格式中的：
tileRows[8 * baseTile + r]  // 原始目标行

只新增：
tileOrder[o]       // 执行位置 o 对应哪个基础 tile
orderCW[o]         // 该 tile 属于任务内哪个 CW
rowToken[8 * o+r]  // 输出槽号以及 HAS_PREV/HAS_NEXT

任务记录包含执行区间、最多 4 个基础 CW ID 和实际 CW 数即可。
这一版可以省掉 rowLocal → swRows 两层目录查询。GPU：
- 用 tileOrder[o] 查 bitmap、values 和真实目标行；
- 用执行位置 o 查 token；
- 只有最终提交输出时才读取真实目标行号。
X 一次加载、一次转换，后续 tile 反复使用
一个 block 进入 SW 时，把最多 4 个 CW 所需的 X fragment 加载并转成 TF32 bits。
按照现有 MMA 映射，一个 CW 对应每线程 8 个 32 位 fragment 值，Q4 合计 32 个。这些值供后续 tile 复用。
实现时优先用静态命名：
x0、x1、x2、x3

按 block 内一致的 orderCW 选择相应 fragment。避免先写一个动态索引的大数组，再假定编译器一定把它放在寄存器中。
同时，把现有 MMA helper 拆成：
toTf32RnaBits(...)
mmaTf32Bits(...)

X 的转换在 SW 开头完成；当前 A fragment 转换一次，供两个 feature part 使用。主 tile 循环里的 MMA 不再重复转换 X。
shared 布局与流水
输出缓存先用：
float outputCache[32][132];

有效 feature 是 128，额外 4 个位置作为初始 stride padding。其容量为：
\[
32\times132\times4=16896\text{ 字节}
\]
约 16.5 KiB。它只是初始布局，是否存在明显 bank conflict 需要测量。
A 使用两个 64-float 缓冲。正确流水是：
加载首个 A tile 和 metadata
同步

for 当前 tile:
    提前加载下一个 A tile 到另一缓冲
    根据当前 token 读取 C
    执行当前 MMA
    保存部分和或提交 Y
    等待下一 A tile 完成
    block 同步
    交换 A 缓冲

下一 tile 的 A 可以预取；它的 C 必须等当前 tile 更新缓存之后再读取。
输出先用标量 atomic 验证，再接现有正确的 float4 重组路径。所有参与者先完成 warp shuffle，再依据输出状态判断是否提交。float4 的收益来自指令和访问组织，数学累加次数仍按每个分量计算。docs.nvidia.com
4. 现在实际需要完成的工作与判断标准
当前工作就按下面五项推进：
顺序	实现内容	需要得到的结果
1	增加 cwCols，先用恒等顺序，打通 Q1	新格式、X 源索引和 MMA 映射正确
2	实现 32 源列小组的轻量分组	重建 A 一致；得到重排前后结构统计
3	生成 Q4 的 tileMax 顺序、token 和槽位	每个 tile 执行一次；每个 SW 目标行最终提交一次
4	实现 Q4 同步 kernel，再接 X 转换外提、float4 和双缓冲	每项优化有相同输入、相同计划的对照
5	测 Products、Arxiv 的 F128/F256	完整调用时间、正确性、寄存器和 shared 资源结果


第一轮只需要比较四组：
1. Acc 基线；
2. 新 Q1，原源列顺序；
3. 新 Q1，轻量分组；
4. 新 Q4，轻量分组。
这样可以分别看清：
- 轻量分组改善了多少；
- 在相同分组上，SW 输出归约又改善了多少；
- 最终距离 Acc 还有多大差距。
每组重点记录：
- **T：**总 tile 数；
- **P：**各 CW 目标行数之和；
- **U：**各 SW 目标行并集大小之和；
- **完整时间：**包括必要的 Y 清零；
- **资源：**寄存器、shared、spill；
- **预处理：**分组和格式构造时间。
其中，无跨 CW 归约时的全局标量更新数为 \(FP\)，Q4 归约后为 \(FU\)。与此同时，新增 shared 部分和读写为 \(2F(P-U)\)。
因此，Q4 是否更快，取决于减少的全局输出能否覆盖 shared、索引和资源占用的新增成本。
如果轻量分组后 P、U 只下降一点，就不能指望输出归约单独填平当前约 2.5 倍的差距；下一步应优先增强有预算的分组，而不是继续扩大缓存。若 P、U 已明显下降但时间不降，则重点检查寄存器 spill、shared 访问和输出指令。
当前就先实现这条闭环：**显式源列映射和 Q1 → 轻量分组 → Q4 输出生命周期归约 → 流水与输出优化 → 与 Acc 完整计时。**这就是第一步所需的 kernel 设计范围。
