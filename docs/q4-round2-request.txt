这是重新分组源列后，CW 内相同输出行合并得更多，P 减少约 37.9%。

所以，Arxiv 上减少的输出更新，目前不足以抵消 Q4 增加的缓存访问、索引、同步和资源占用成本。 至于其中哪一项占主导，现有完整时间不能分离出来。尤其 F128 的最快 Q4 仍慢于原序 Q1 的 2.41 ms，不能将 Q4 设成所有情况的默认最优路径。完整消融。
二、第一优先级：补上标量输出的 Pipeline
这是我认为最应该马上实现的一项。
当前代码把两个优化绑定了：
Wide     = V >= 3;
Pipeline = V == 4;

因此，现在所有使用 A 双缓冲的 Q4，都同时使用了 float4 输出。代码位置：column_q4.cu。
你的消融实际只有下面三个组合：
A 加载方式	scalar atomic	float4 atomic
同步加载	Q4 Bits，已有	Q4 Float4，已有
双缓冲加载	缺失，优先补上	Q4 Pipeline，已有


这个缺口在 Products/F256 上特别明显：
- Bits：97.35 ms。
- 加 float4：108.25 ms。
- float4 再加双缓冲：110.62 ms。
这些数据证明当前 float4 实现有负收益，还不能据此判断“F256 不适合双缓冲”。Products/F256 原始 CSV。
具体怎么改
将 UseAsyncA 和 UseFloat4 拆成独立的编译期开关，首先只增加一个配置：
Q4_bits_scalar_pipeline

它的行为应当是：
- 沿用 Bits 的 X 转换外提与静态寄存器 fragment。
- 沿用当前 Q4 的 tileOrder、rowToken 和 C 缓存。
- A 使用现有双缓冲与 cp.async。
- 最终输出继续使用 Bits 的 scalar atomic。
- 本版本先保持 H=32，方便单独观察流水收益。
当前流水中的关键时序可以保留：预取下一块 A → 计算并完成当前 tile 的 C 更新 → 等待复制 → CTA 同步 → 下一 tile。 现有实现没有提前读取下一 tile 的 C，这一点符合生命周期依赖。主循环。
另外，当前 float4 路径每个 part 在源码中做了 16 次 shuffle 来整理四个输出值，这本身就有成本。float4 的原子性也是分别针对四个 float 元素提供的，数学上的输出更新仍然是 \(FU\)，不会因为使用 float4 自动变成 \(FU/4\)。输出代码。CUDA C++ Programming Guide
这一项的价值是：先把流水本身的收益测清楚，让 Products/F256 有机会用上双缓冲，同时避免承担当前 float4 的转置成本。
三、第二优先级：固定 Q4，缩小实际用不到的 C 缓存
当前所有 Q4 都分配：
__shared__ float cache[32][132];

但离线统计已经给出了实际需求：
- Arxiv：最大 14 个槽。
- Products：最大 20 个槽。
也就是说，这两张图都没有用满 32 槽，却一直支付 32 槽的 shared 占用。报告中的 Q4 最大驻留量都是 5 CTA/SM。缓存声明；资源与峰值统计。
具体怎么改
增加三个编译期容量：
H = 16, 24, 32

建好同一份离线计划后，在启动端选择最小足够容量：
H = peakSlots <= 16 ? 16 :
    peakSlots <= 24 ? 24 : 32;

对应 shared 占用如下：
缓存容量 H	C 缓存	加上 A 双缓冲后的总量
16	8,448 B	8,960 B
24	12,672 B	13,184 B
32	16,896 B	17,408 B


SW 仍然是四个 CW，X 仍然加载四份 fragment，生命周期和全局输出次数都保持原样。 这里只是利用已知上界缩小缓存。
为什么现有 token 可以直接使用？因为离线分配器每次取最低空闲槽：
slot = __builtin_ctz(~occupied);

如果曾经分配到槽 s，那么当时至少需要 s+1 个槽，所以最大槽号一定小于记录的历史峰值。代码位置：槽分配与释放。
实现时有两个细节必须保留：
- token 仍用 token & 31 解码槽号，不能改成 token & (H-1)。 H=24 不是二次幂，而且这次没有改变 token 编码。
- 上传前检查所有带 PREV／NEXT 状态的 token 都满足 slot < H；q4Attributes 也要查询实际选中的 H 实例。
按 shared 上限 100 KiB、每线程寄存器保持当前范围估算，H24 有机会从 5 CTA/SM 提高到约 7，H16 有机会到约 8。实际值应重新通过 occupancy API 查询；提高驻留量能否转化成速度，还取决于等待和原子压力。CUDA 当前规格表区分了 SM 12.x 的 128 KiB 统一缓存容量与最多 100 KiB shared 配置，计算时不要混用。CUDA Programming Guide
对 Arxiv，这项尤其值得先试：它的归约比例较小，更需要压低 Q4 的固定资源成本。
四、第三优先级：给 A 的 shared tile 加 XOR 布局
这项比直接猜测“是不是 bank conflict”更具体，因为当前地址模式可以算出来。
当前 A fragment 的加载是：
a[g * 8 + k]
a[g * 8 + k + 4]

其中：
g = lane / 4;   // 0..7
k = lane % 4;   // 0..3

代码位置：A fragment 加载。
shared 的相邻 32 位字映射到相邻 bank。因此，对第一条标量加载：
\[
bank=(8g+k)\bmod32
\]
g 与 g+4 对应的地址相差 32 个 float，地址不同，但 bank 相同。按这个标量发指令模式，一次 warp 加载只使用 16 个 bank，每个 bank 对应两个不同地址；第二条加载同理。CUDA Programming Guide
用一个不增加 shared 空间的映射解决
定义逻辑 A 坐标到 shared 地址的映射：
\[
\operatorname{phys}(r,c)=8r+\left(c\oplus(r\&4)\right)
\]
具体修改很小。
写入 A 时：
// t 仍是原始逻辑位置，用于 bitmap 判断与 popcount。
unsigned physical = t ^ ((t >> 3) & 4);

// 同步加载写入 a[physical]。
// cp.async 的 shared 目标也改成 a + physical。

读取 A fragment 时：
unsigned swizzle = g & 4;

float a0 = a[g * 8 + (k ^ swizzle)];
float a1 = a[g * 8 + ((k + 4) ^ swizzle)];

bitmap、values、压缩值索引全部继续按原来的逻辑位置计算，改变的只是 A 在 shared 里的物理摆放。
我做了完整 lane 枚举，结果是：
地址模式	每条 A 标量加载使用的 bank 数	每个 bank 最多不同地址数
当前布局	16	2
XOR 布局	32	1


同时，staging 写入仍然是 warp 内原来那些位置的置换，64 个 shared 元素一一对应，没有增加容量，也没有引入 staging 的重复 bank。
这里验证的是地址映射。编译后仍要看 SASS 是否按预期加载，再通过同配置计时确认收益；它不会自动意味着整个 kernel 加速两倍。
C 缓存的 132 stride 暂时保持
C 的访问受实际 slot 组合影响：
\[
bank=(132\,slot+feature)\bmod32
\]
132 并不能保证任意活跃槽组合都无冲突。下一轮先裁容量；如果还需要优化 C 布局，可以直接从离线 rowToken 模拟实际 PREV／NEXT 访问的 bank 分布，再选择布局或槽位分配策略。这样即使暂时没有 Nsight 计数器权限，也能得到有针对性的访问模式证据。
五、轻量重排下一步怎么做：先扰动整个 SW 的执行顺序
你的源列分组已经在 Products 上带来了明显的结构收益。下一轮可以先保留这份分组，增加一个很便宜的对照：只重排完整的 Q4Task 记录。
这里要明确两个不同的目标。
对于固定的 32 个源列：
\[
U_{\mathrm{SW}}
=
\left|\bigcup_{c\in\mathrm{SW}}N(c)\right|
\]
所以：
- 在同一 SW 内重新划分四个 CW，可以继续降低 P、tile 数和 shared 工作。
- 只要这 32 个源列不变，U 就不变，Q4 的 \(FU\) 个全局更新也不变。
- 重排整个 SW 的执行顺序，P、T、U 都不变，测试的是运行时局部性和调度敏感性。
这个区别直接来自当前分组与计划构造方式。格式代码。
建议的单一对照
在连续 256 个 SW task 的局部窗口里：
1. 用 L = task.end - task.begin 表示 tile 数。
2. 按 tile 数的数量级分桶。
3. 同桶任务用固定种子的 hash 打散。
4. 将完整 task 放回该桶原来占据的位置。
这样可以大致保持每个位置的工作量等级，同时改变相近工作量任务之间的邻接关系。
实现只需搬动 Q4Task，其中的 begin/end/cw[4]/count 整体搬走；内部 tileOrder、token 和生命周期不用改。当前 kernel 本来就通过 tasks[blockIdx.x] 读取任务，适合做这个实验。F256 继续保留原来的两个 feature CTA 映射。任务读取与启动。
为什么值得测？ 当前任务顺序沿用 MinHash 分组顺序，共享某个签名邻居的源列可能集中出现。相邻 CTA 因此可能更集中地更新相同输出行。这既可能改善缓存局部性，也可能增加原子竞争，现有数据无法判断哪种影响占主导。
这个对照可以回答“Q4 是否对执行顺序敏感”，但不能单独证明 Arxiv 的 Q1 退化已经找到原因。构造计划时顺便保存每 CW／SW 的 tile 数分位数、最大值以及每 SW 的 P、U、峰值槽数就够了，暂时无需再引入新的分组搜索算法。
